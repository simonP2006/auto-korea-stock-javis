# PRD: KOSPI/KOSDAQ 종목 기술적 완성도 분석 및 선별 시스템

> **제1 핵심 목적**: (1) 종목 스크리너에게 특정일 데이터를 수집·필터링하도록 명령할 수 있어야 한다. (2) 사용자가 필터 조건을 fine-tuning하기 쉽게 도울 수 있어야 한다. **이것이 가장 큰 목표이다.**

---

## 1. 제품 정체성

**한 줄 정의**: 기존 kiwoom-rest-trader 종목 스크리너를 AI 에이전트가 오케스트레이션하고, 5-Stage 필터 조건의 fine-tuning을 자연어 대화로 지원하는 로컬 자동화 시스템.

**"분석"의 범위**: 시스템 이름에 "분석 및 선별"이 포함되어 있다. 이 PRD(Phase 1)에서 "분석"이란 다음을 의미한다: (a) 종목별 탈락사유의 Stage·조건·수치 수준 설명(FR-3), (b) 탈락 기준값과 실제값의 gap 제시(FR-3.4), (c) 이론적 근거에 기반한 파라미터 조정 가이드(FR-7). 연속 점수(예: "85점/100점")를 산출하는 정량 스코어링은 Phase 1 범위에 포함하지 않는다. 기존 시스템의 `stageMasterFilter.py`(연속 수치 기반 독립 필터)를 활용한 스코어링 연동은 Phase 2에서 검토한다(§12 참조).

**왜 존재하는가**:

사용자는 이미 Kiwoom REST API 기반 종목 스크리너(`kiwoom-rest-trader`)를 보유하고 있다. 이 스크리너는 KOSPI/KOSDAQ ~2,500개 종목의 차트·수급·재무 데이터를 수집하고, 5-Stage 순차 필터로 기술적 조건에 부합하는 종목을 선별한다. 수집과 필터링은 동작하지만, 다음 두 가지 장벽이 사용자의 효과적 활용을 가로막는다:

1. **실행 장벽**: 터미널에서 Python 명령어를 직접 입력해야 하며, 에러 발생 시 대처할 수 없다.
2. **튜닝 장벽**: 필터 조건 파라미터(MA 허용오차, 수급 임계값 등)가 Python 코드 상수로 내장되어 있어, 비기술 사용자가 (a) 파라미터의 의미를 이해하거나, (b) 값을 변경하거나, (c) 변경의 영향을 예측하는 것이 불가능하다.

이 시스템은 AI 에이전트가 이 두 장벽을 대행함으로써, 코드 구현 능력이 없는 사용자도 자연어 대화만으로 종목 선별과 필터 최적화를 수행할 수 있게 한다.

**기존 시스템(kiwoom-rest-trader)과의 관계**: 이 시스템은 kiwoom-rest-trader를 대체하지 않는다. kiwoom-rest-trader는 데이터 수집·필터링의 **실행 엔진**이고, 이 시스템은 그 엔진을 지능적으로 **운전하는 운전자**다.

**구현 형태**: 이 시스템은 **Claude Code 대화 세션** 안에서 동작한다. 별도의 독립 애플리케이션이나 상주 서버가 아니다. 사용자가 Claude Code를 열고 자연어로 요청하면, Claude Code가 Bash 도구를 통해 kiwoom-rest-trader의 Python 명령을 실행하고, Read/Edit 도구를 통해 필터 파라미터를 읽고 수정한다. 즉:
- **오케스트레이터** = Claude Code (AI 에이전트)
- **실행 환경** = 사용자의 로컬 macOS 터미널
- **인터페이스** = Claude Code의 자연어 대화

이 형태의 제약: (a) Claude Code 세션이 열려 있어야 동작한다 (백그라운드 자동 실행 불가). (b) 장시간 실행 명령의 중간 진행 상태를 실시간으로 스트리밍할 수 없다 (Bash 도구는 명령 완료 후 stdout 반환). (c) 세션 간 상태는 파일 시스템에 저장된 데이터(reports/, 백업 파일)를 통해 유지된다.

**최종 산출물의 형태**: 이 PRD를 기반으로 workflow.md가 생성되며, 그 Implementation 단계의 산출물은 **Claude Code가 대화 시 참조하는 CLAUDE.md 및 skill 문서 세트**다. 독립 실행 가능한 소프트웨어나 상주 서버를 구축하는 것이 아니다. 산출물은 Claude Code의 대화 행동 규칙(자연어 해석, 명령 실행, 파라미터 변경, 결과 보고)을 정의하는 프롬프트·스킬 파일이며, kiwoom-rest-trader 자체는 수정하지 않는다 (파라미터 상수 값 변경 제외).

## 2. 문제 정의

### 2.1 사용자가 직면한 문제

KOSPI/KOSDAQ 전 종목(~2,500개) 중에서 기술적 분석 기준으로 유망한 종목을 선별하려 한다. 수동 분석은 물리적으로 불가능하다(2,500종목 × 6개 데이터 × 5-Stage 판정).

기존 kiwoom-rest-trader 스크리너가 이 문제를 해결하지만, 사용자는 다음을 할 수 없다:

| # | 할 수 없는 것 | 근본 원인 | 제1 핵심 목적 연결 |
|---|---|---|---|
| P-1 | 스크리너를 자연어로 실행 | Python 명령어 직접 입력 필요 | 핵심목적 1 |
| P-2 | 필터 파라미터의 의미 파악 | Python 코드 읽기 불가 | 핵심목적 2 전제조건 |
| P-3 | 필터 파라미터 값 변경 | Python 코드 수정 불가 | 핵심목적 2 |
| P-4 | 변경 영향 예측 | 재실행 없이는 알 수 없음 | 핵심목적 2 |
| P-5 | 특정 종목 탈락 원인 분석 | Stage별 수치 비교 불가 | 핵심목적 2 |
| P-6 | 시장 상황에 맞는 파라미터 조정 | 이론적 맥락 부재 | 핵심목적 2 |
| P-7 | 필터 변경 전후 비교 | 결과 대조 수작업 불가 | 핵심목적 2 |

> **P-2 ~ P-7은 모두 "필터 조건 fine-tuning"(핵심목적 2)에 속한다. 이것이 가장 큰 목표다.**

### 2.2 기존 시스템 개요

kiwoom-rest-trader는 로컬에서 작동하는 Python 기반 종목 스크리너다.

**데이터 수집**: Kiwoom REST API를 통해 종목별 차트 데이터(60분/120분/240분/일봉) + 투자자 수급 + 재무정보를 수집한다. 각 종목별 6개 Markdown 파일이 `reports/YYYYMMDD/<종목명(코드)>/` 하위에 저장된다.

| 파일 | 내용 | MA 정보 |
|---|---|---|
| chart60.md | 60분봉 시계열 (16봉) | MA10, MA20, MA60, MA306 |
| chart120.md | 120분봉 시계열 (16봉) | MA10, MA20, MA60, MA306 |
| chart240.md | 240분봉 시계열 (16봉) | MA10, MA20, MA60, MA306 |
| chartDay.md | 일봉 시계열 (16봉) | MA10, MA20, MA60, MA306, MA612 |
| investor.md | 투자자별 매매 현황 (16거래일) | 개인, 외국인, 기관계 |
| finance.md | 재무 요약 | PER, EPS, ROE, PBR, 당기순이익 |

**5-Stage 순차 필터링**: 종목별로 Stage 1→5를 순서대로 평가하며, 한 Stage라도 탈락하면 이후 Stage를 평가하지 않는다(early exit).

| Stage | 모듈 | 입력 | 판정 기준 요약 |
|---|---|---|---|
| 1 | chart60_120Filter | chart60.md + chart120.md | 60분/120분봉 MA 4선 정배열, Type A~E 5가지 패턴 매칭 |
| 2 | chart240Filter | chart240.md | 240분봉 장기추세 — MA60 ≥ MA306 × 0.975 (최근 3봉 전부) |
| 2-1 | chartDayPreFilter | chartDay.md | 당일 +15% 이상 급등 종목 사전 제외 |
| 3 | chartDayFilter | chartDay.md | 일봉 MA 정배열(3봉 중 2봉) + MA612 밴드(-15%~+50%) + 양봉 |
| 4 | investorFilter | investor.md | 외국인·기관·개인 수급 조건 (연속매도/매수 임계값) |
| 5 | financeFilter | finance.md | 당기순이익 적자(< 0) 종목 제외 |

**실행 방식 3가지**:

| 방식 | 명령 | 용도 |
|---|---|---|
| A (통합) | `python -m scripts.run_full_research_flow YYYYMMDD` | 수집 + 필터 일괄 실행 |
| B (분리) | `run_prefetch` 1회 → `run_filters` N회 | 필터 조건 반복 튜닝용 (API 재호출 없음) |
| C (탈락분석) | `Filter_condition_update YYYYMMDD` | 특정 종목의 Stage별 탈락 사유 추적 |

**핵심 산출물**:

| 산출물 | 파일 | 설명 |
|---|---|---|
| Stage별 통과 목록 | `stage1_chart60_120_passed.md` ~ `stage5_finance_passed.md` | 각 Stage 통과 종목 |
| 최종 선별 결과 | `researchedCompany.md` | 5-Stage 전부 통과한 종목 |
| 탈락사유 분석 | `masterReference.log` | 관심 종목의 탈락 Stage 및 구체적 사유 |

## 3. 대상 사용자

> **제1 핵심 목적 연결**: 비기술 사용자이기 때문에 핵심목적 1(스크리너 실행 대행)과 핵심목적 2(필터 튜닝 지원) 모두가 필요하다. 사용자 프로필은 두 핵심목적의 존재 이유이자 설계 제약이다.

**주 대상: 비기술 사용자** [R1-S03-F5 확인]

- **코드 능력**: 없음 — Python 코드를 읽거나 수정할 수 없다 (사용자 원문: "코드 구현 능력이 전혀 없다")
- **분석 능력**: 기술적 분석에 대한 개념적 이해 있음 — "정배열", "수급", "이평선" 등 기본 용어는 알지만, 수식/파라미터 수준의 전문 지식은 제한적
- **행동 패턴**: 결과를 보면서 직관적으로 판단 → "이 종목은 포함되어야 하는데" / "필터가 너무 엄격해" → 조정 요청
- **언어**: 한국어 전용
- **에러 대응**: 불가능 — "안 돼" 이상의 진단 불가, AI가 해결해주기를 기대
- **이탈 트리거**: 영어 에러 메시지, 구글링 필요 상황, 5분 초과 무피드백 대기 [R1-T03]

**핵심 대화 패턴** (시스템이 지원해야 하는 자연어 입력):

```
- "오늘 종목 스캔해줘"                          → 스크리너 실행 (FR-1)
- "오늘 결과 보여줘"                             → 필터 결과 해석 (FR-2)
- "삼성전자가 왜 빠졌어?"                        → 탈락사유 분석 (FR-3)
- "Stage 1 조건 보여줘"                          → 파라미터 가시화 (FR-4)
- "외국인 매도 조건을 좀 완화해줘"               → 파라미터 변경 (FR-5)
- "데이터는 그대로 두고 필터만 다시 돌려줘"      → 재실행 (FR-6)
- "원래대로 되돌려줘"                            → 복원 (FR-6)
- "정배열 조건이 너무 엄격한 것 같아"            → 이론 기반 가이드 (FR-7)
- "어제랑 오늘 결과 비교해줘"                    → 결과 비교 (FR-2)
```

## 4. 핵심 요구사항

> 모든 요구사항은 제1 핵심 목적과의 연결을 명시한다. 연결되지 않는 항목은 포함하지 않았다.
>
> **구현 우선순위**: FR-1(실행 기반, 나머지 FR의 전제조건) → FR-4/FR-5(파라미터 가시화+변경, 핵심목적 2 핵심) → FR-3(탈락 분석) → FR-6(반복 실험) → FR-2(결과 해석) → FR-7(이론 가이드) → FR-8(면책).

### FR-1: 종목 스크리너 실행 명령

> **제1 핵심 목적 연결**: 종목 스크리너에게 데이터 수집·필터링을 명령할 수 있어야 한다 (핵심목적 1).

자연어 명령으로 kiwoom-rest-trader의 데이터 수집 및 필터링 파이프라인을 실행할 수 있어야 한다.

**요구사항**:

| ID | 요구 | 비고 |
|---|---|---|
| FR-1.1 | "오늘 종목 스캔해줘" → 방식 A(`run_full_research_flow`) 자동 실행 | 날짜 생략 시 오늘 |
| FR-1.2 | "YYYYMMDD 데이터로 필터만 돌려줘" → 방식 B(`run_filters`) 실행 | 수집 데이터 재사용 |
| FR-1.3 | 다중 날짜 실행 지원 ("이번 주 월~금 전부 수집해줘") | 순차 실행 |
| FR-1.4 | 실행 전 예상 소요시간 한국어 안내 + 실행 완료 후 결과 보고. 장시간 명령(수집 등)은 **방식 B(run_prefetch + run_filters 분리 실행)**로 단계를 분할하여 각 완료 시 중간 보고. 방식 A(run_full_research_flow)의 내부 분할은 구현하지 않는다 | Claude Code Bash 도구는 명령 완료 후 stdout 반환이므로, 단일 명령 실행 중 실시간 스트리밍 불가. §1 구현 형태 제약 (b) 참조 |
| FR-1.5 | 에러 발생 시 한국어 원인·대응 안내 | "KRX 서버 연결 실패. 잠시 후 다시 시도합니다" |
| FR-1.6 | kiwoom-rest-trader 가상환경 자동 활성화 | 사용자가 `.venv/bin/activate`를 몰라도 됨 |
| FR-1.7 | 초회 실행 전 전제조건 검증: (a) kiwoom-rest-trader 프로젝트 존재, (b) `.venv` 활성화 가능, (c) `reports/` 쓰기 권한, (d) 필수 Python 패키지 설치 상태. 미충족 시 한국어 안내 + 자동 복구 가능한 항목은 자동 수행 | 비기술 사용자는 전제 미충족을 자력 해결 불가 |

### FR-2: 필터 결과 해석

> **제1 핵심 목적 연결**: 필터 결과를 이해해야 fine-tuning이 가능하다 (핵심목적 2 전제조건).

5-Stage 필터링 결과를 사용자가 이해할 수 있는 한국어로 해석·보고해야 한다.

**요구사항**:

| ID | 요구 | 비고 |
|---|---|---|
| FR-2.1 | Stage별 통과/탈락 종목 수 요약 테이블 | "Stage 1: 350→82, Stage 2: 82→45, ..." |

### 5.2 튜닝 인터랙션 패턴

> AI가 지원해야 하는 필터 fine-tuning 대화의 전형적 패턴 4가지.

#### 패턴 A: 결과 기반 조정 ("통과 종목이 너무 적어/많아")

```
사용자: "오늘 결과에서 통과한 게 3개뿐이야. 좀 더 나왔으면 좋겠어"
   ↓
AI: Stage별 탈락 분포 분석 → 가장 많이 걸러진 Stage 식별
   "Stage 1에서 입력 350개 중 268개(77%)가 탈락했습니다.
    Stage 1 Type A 허용오차(-3.5%)를 -5.0%로 완화하면
    약 15개 종목이 추가 통과할 것으로 예상됩니다."
   ↓
사용자: "해봐"
   ↓
AI: 파라미터 변경 → run_filters 재실행 → 비교 결과 보고
   "변경 전 3개 → 변경 후 11개. 추가 8개: [목록]"
```

#### 패턴 B: 종목 기반 조정 ("이 종목은 포함되어야 해")

```
사용자: "대한전선이 왜 빠졌어?"
   ↓
AI: 해당 종목 데이터 읽기 + masterReference 분석
   "Stage 3(일봉 정배열)에서 탈락. MA20이 MA60의 0.94배로,
    기준(0.95배, 허용오차 -5%)에 0.01(1%p) 미달입니다."
   ↓
사용자: "이 정도면 통과시켜도 되지 않아?"
   ↓
AI: "Stage 3 MA 허용오차를 -6%로 완화하면 대한전선 포함 약 5개 추가.
    단, Minervini 기준으로 -5%는 이미 관대한 편입니다.
    더 완화하면 추세 확인 신뢰도가 낮아질 수 있습니다."
```

#### 패턴 C: 이론 기반 조정 ("시장이 약세/강세인데")

```
사용자: "요즘 시장이 약세인데 필터를 어떻게 바꿔야 해?"
   ↓
AI: "약세장에서는 두 가지 방향이 있습니다:
    1. 방어적: Stage 4 수급 조건 강화 (외국인 매도 2일→1일)
       → 기관·외국인이 아직 이탈하지 않은 종목만 선별
    2. 기회적: Stage 1 정배열 조건 완화 + Stage 2 장기추세 강화
       → 바닥에서 반등 준비 중인 종목 탐색
    어느 방향으로 가시겠습니까?"
```

#### 패턴 D: 실험 비교 ("어떤 설정이 나아?")

```
사용자: "어제 설정이랑 오늘 설정 중 어떤 게 나아?"
   ↓
AI: 두 설정의 통과 종목 비교
   "설정 A(어제): 15개 통과 — [목록]
    설정 B(오늘): 22개 통과 — [목록]
    공통: 12개 | A에만: 3개 | B에만: 10개
    B에서 추가된 10개는 주로 Stage 1 Type A에서 허용오차 완화 효과입니다."
```

### 5.3 이론적 프레임워크 ↔ 기존 필터 매핑

> 각 Stage의 이론적 근거 상세는 **부록 A** 참조. 여기서는 AI가 FR-7(이론 기반 튜닝 가이드)을 실행할 때 사용하는 이론↔필터 매핑만 요약한다. [R1-T02, R2-T05]

| 이론 | 기존 필터 매핑 | 파라미터 조정 시 앵커 |
|---|---|---|
| **Minervini SEPA** | Stage 1 (Type A), Stage 3 (일봉) | 정배열 허용오차 통상 -2%~-5% |
| **Weinstein Stage Analysis** | Stage 2, Stage 1 Type B | MA60≥MA306 기준 |
| **Wyckoff** | Stage 4 (수급 조건) | 스마트머니 이탈 징후 |
| **VCP** | Stage 1 Type C, E | 수렴 폭 3.5%~10% |
| **CANSLIM** | Stage 5 (당기순이익) | 적자 제외 |

**"기술적 완성도"의 운영적 정의**: 5-Stage 필터 조건을 모두 충족하는 것. 다중 시간 프레임 정배열 + 장기 추세 상승 + 과열 제외 + 스마트머니 미이탈 + 최소 수익성.

### 5.4 공유 상수 주의사항

일부 파라미터는 여러 Type에서 공유된다. 하나를 변경하면 관련 Type 모두에 영향이 미친다.

| 공유 상수 | 현재 값 | 영향 범위 | 주의 |
|---|---|---|---|
| `_ALIGN_TOL_LOOSE` (공유 정배열 허용오차) | -1.5% (0.015) | Type B 60분 정배열, Type B MA60-MA306, Type C MA60-MA306, Type D 60분 정배열 | 이 값 변경 시 Type B/C/D의 여러 서브조건이 동시에 영향. 사용자에게 영향 범위를 반드시 안내 |

> **⚠️ 규칙**: 공유 상수 변경 시 AI는 영향받는 모든 Type과 서브조건을 나열하여 사용자에게 안내해야 한다. 특정 Type만 변경하려면 해당 Type 전용 상수를 신설하는 방향을 제안해야 한다 (TS-1의 "로직 미수정" 규칙과 충돌하므로 사용자 명시적 승인 필요).

### 5.5 튜닝 안전 규칙

> **제1 핵심 목적 연결**: fine-tuning(핵심목적 2)의 안전한 실행을 보장하는 가드레일이다.

필터 파라미터 변경 시 지켜야 하는 안전 규칙:

| ID | 규칙 | 근거 |
|---|---|---|
| TS-1 | 변경 대상은 Python 모듈의 `Final` 타입 상수 값만. 필터 로직 코드(조건문, 루프 등)는 수정하지 않는다. **예외**: Stage 5(financeFilter)는 현재 `Final` 상수가 없으므로 Phase 1에서 튜닝 불가 (§5.1 Stage 5 참조) | 기능적 무결성 보장 |
| TS-2 | 모든 변경 전 원본 파일 백업 생성 | 복원 경로 보장 |
| TS-2a | 백업 생명주기: 동일 파일의 백업은 **최근 5개만 유지**. 6번째 생성 시 가장 오래된 백업 자동 삭제. 삭제 전 해당 설정이 튜닝 로그(FR-6.6)에 기록되었는지 확인 | 디스크 누적 방지 + 복원 경로 유지 |
| TS-3 | 파라미터 타입별 물리적 범위 검증: (a) 허용오차(tolerance) = 0.00~0.50, (b) 비율(ratio/threshold) = 0.0~1.0, (c) 정수 임계값 = 1~16 (16봉 데이터 내), (d) 밴드 상·하한 = 각 파라미터의 논리적 범위 내. 범위 밖이면 경고 | 무의미한 값 방지 |
| TS-4 | 한 번에 하나의 파라미터만 변경 권장 (복수 변경 시 영향 분리 불가 경고) | 인과 추적 가능성 |
| TS-5 | 변경 후 반드시 재필터 실행 제안 | 효과 즉시 확인 |

3. 실행 완료 후 AI: Stage별 통과/탈락 통계 + 최종 선별 종목 목록 + 면책조항 자동 보고
4. 사용자: "OO전자 왜 빠졌어?" → 탈락 사유 구체 설명
5. 사용자: "결과 괜찮네" → 세션 종료

### 7.2 필터 튜닝 세션 시나리오

1. 사용자: 결과를 보고 불만족 표현 ("너무 적어" / "이 종목은 포함되어야 해")
2. AI: Stage별 탈락 분포 분석 + 파라미터 조정 방향 제안 (이론적 근거 포함)
3. 사용자: 조정 승인 ("해봐")
4. AI: 파라미터 변경 → `run_filters` 재실행 (API 호출 0회, 빠름) → 전후 비교 보고
5. 2-4 반복 (만족할 때까지)
6. 사용자: "이걸로 확정" 또는 "원래대로 되돌려줘"

## 9. 제약 사항

> **제1 핵심 목적 연결**: 아래 제약은 핵심목적 1(실행 환경·API 의존)과 핵심목적 2(파라미터 타입 제약·사용자 능력)의 경계 조건을 정의한다.

### 9.1 로컬 실행 전제 (핵심목적 1, 2 공통)

- 모든 기능은 사용자의 로컬 macOS 컴퓨터에서 실행된다.
- 네트워크 의존: Kiwoom REST API (데이터 수집 시에만), Anthropic API (AI 대화).
- 기존 kiwoom-rest-trader가 사전 설치·설정 완료된 상태를 전제한다 (가상환경, Kiwoom API 인증 등).

### 9.2 기존 시스템 제약 (핵심목적 1, 2 공통)

- 데이터 수집은 Kiwoom REST API에 의존한다. 거래시간 종료 후 API가 가용해야 한다.
- 종목별 6개 API 호출이 필요하며, API 간 0.3초·종목 간 0.5초 페이싱이 적용된다. 수집 시간은 종목 수에 비례한다.
- 필터 파라미터는 Python 코드의 `typing.Final` 타입 상수로 정의되어 있다. AI가 수정 시 값의 타입(int/float)과 의미적 범위를 준수해야 한다.
- 필터는 사전 저장된 Markdown 파일만 읽으므로, 데이터 수집(prefetch)이 선행되어야 한다.

### 9.3 법적 제약 (핵심목적 1, 2 공통)

- 한국 금융규제상 무면허 투자 조언이 불가하다. [R1-S03-F8]
- 모든 출력은 "분석 도구"로 프레이밍한다. "매수/매도 추천" 표현은 사용하지 않는다.
- 모든 종목 결과 출력에 면책조항을 포함한다.

### 9.4 사용자 제약 (핵심목적 1, 2 공통)

- 사용자는 Python 코드를 읽거나 수정할 수 없다. 모든 코드 작업은 AI가 대행한다.
- 터미널 명령어 직접 입력은 최소화한다. AI가 명령 실행을 대행한다.
- 영어 에러 메시지는 이탈 트리거다. 모든 사용자 대면 메시지는 한국어여야 한다.

### C.3 연구 활용 범위 선언

final-research.md는 **새로운 stock-scanner 시스템**(DuckDB, pandas-ta-classic, 6-서브스코어) 구축을 위해 조사되었다. 이 PRD(Phase 1)는 **기존 kiwoom-rest-trader 활용**으로 범위를 축소했으므로, 연구의 직접 활용 비율은 아래와 같다:

| 연구 영역 | Phase 1 활용도 | 비고 |
|---|---|---|
| 사용자 분석 (R1-T03) | ~100% | 대화 패턴·이탈 트리거·언어 규칙 |
| 이론 프레임워크 (R2-T05) | ~80% | FR-7 이론 가이드 + §5.3 매핑 |
| Claude Code 역량 (R2-T06, R3-T02/T03) | ~60% | 오케스트레이션·스킬 설계 패턴 |
