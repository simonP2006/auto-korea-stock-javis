# S01: 5개 영역 스펙트럼 포지셔닝 + Phase 2 관점별 토론

## Phase 1 통합: 5개 영역 스펙트럼

10개 브랜치 (5팀 × 2개 상충 접근) 조사 결과를 하나의 스펙트럼에 포지셔닝.

```
Workflow Script:
  선언적 ←──────●─────→ 절차적
                 ↑ 75% 절차적 (Hybrid: 핵심 파이프라인=절차적, 해석/보고=선언적)

Agent Orchestration:
  중앙 집중 ←●─────────────→ 분산
             ↑ 90% 중앙 (일일 파이프라인. Phase 2+ 심층분석만 sub-agent fork)

Skills & Hooks:
  범용 ←────────────●──→ 특화
                     ↑ 85% 특화 (도메인 지식 내장이 핵심 가치)

Verification:
  엄격 ←──────●────────→ 선택적
              ↑ 70% 엄격 (Gate 1,3 전수 + Gate 2,4 샘플링)

State Management:
  파일 기반 ←●──────────────→ 상태 머신
             ↑ 80% 파일 기반 (4단계 순차에 FSM은 과설계)
```

### 수렴 패턴

5개 팀이 독립 조사했으나 일관된 패턴 발견:
1. **순수 극단은 모두 배제**: 5개 영역 모두 Hybrid/중도 포지션 수렴
2. **"절차적/엄격/특화" 쪽으로 편향**: 금융 분석 도구의 정확도 요구 때문
3. **"과설계 경계" 의식**: FSM, Agent Swarm, Full-Defensive 모두 "비용 대비 이점 부족"으로 배제
4. **로컬 실행 제약 영향 미미**: [LOCAL-BLOCKED] 0개, [LOCAL-PARTIAL] 3개(모두 회피 가능)

## Phase 2: 4개 관점별 토론 결과

Phase 1의 10개 브랜치 결과를 4가지 우선순위 관점에서 재평가.

### 관점 A: 워크플로우 표현력 우선

**질문**: "workflow.md가 충분히 정밀하게 표현하는가?"

| 구성 요소 | 가장 정밀한 패턴 | 근거 |
|-----------|----------------|------|
| 데이터 수집 | 절차적 (5개 장애 모드별 분기) | 선언적 "On Failure: cache" 는 5개 모드를 1개로 축소 |
| 지표 계산 | 절차적 (pandas-ta 함수 시그니처) | `ta.bbands(close, length=20, std=2)` 가 사양 그 자체 |
| 스코어링 | 절차적 (6 서브스코어 공식) | 가중치·기준·매핑이 제품 요구사항 |
| 리포트 | 선언적 (종료 기준만) | 형식 유연성이 자산 |

**결론**: 표현력 관점에서 절차적 > 선언적 (3:1). Hybrid가 최적 표현력.

### 관점 B: 구현 안정성 우선

**질문**: "가장 안정적으로 작동하는 패턴은?"

| 패턴 | 안정성 기여 | 비용 |
|------|-----------|------|
| 중앙 집중 오케스트레이션 | 단일 로그 스트림, 예측 가능 실패 | LOW |
| Targeted Strict 검증 | 6/6 핵심 실패 모드 방어 | ~780줄 |
| 파일 기반 상태 + guard | 투명한 상태, 간단한 복구 | ~520줄 |
| 특화 hook (validate_pykrx) | pykrx 특유 장애 탐지 | ~100줄 |

**결론**: 안정성 관점에서 Targeted Strict + 파일 기반 상태가 최소 비용 최대 효과.

### 관점 C: 구현 속도 우선

**질문**: "가장 빠르게 구현 가능한 패턴은?"

| 구성 요소 | 최소 구현 | 생략하는 것 | 위험 |
|-----------|----------|-----------|------|
| workflow.md | 선언적 (~150줄) | 구체적 실행 지침 | 오케스트레이터 설정 복잡 |
| 검증 | 행 수만 체크 (~100줄) | NaN, 분포, 이상탐지 | FM-4,5 미탐지 |
| 상태 | 없음 (재실행=복구) | 체크포인트, 복구 | 5년 로드 중단 시 처음부터 |

**결론**: 속도 관점에서 최소 구현 가능하나, **금융 도구로서 사용자 신뢰 위험** → 절대 기준 1(품질)에 의해 속도 양보.

### 관점 D: 유지보수/확장성 우선

**질문**: "6개월 후 수정/확장이 가장 쉬운 패턴은?"

| 패턴 | 유지보수성 | 확장성 |
|------|----------|--------|
| scoring_config.yaml SOT | ✅ 단일 수정점 | ✅ 새 서브스코어 추가 용이 |
| 특화 스킬 + references/ 분리 | ✅ 스킬 본체 수정 없이 설정 변경 | ✅ 새 스킬 추가 가능 |
| 파일 기반 상태 | ✅ JSON 스키마 확장 용이 | ⚠ 병렬 파이프라인 시 한계 |
| 중앙 집중 오케스트레이션 | ✅ 단순 | ⚠ 복잡 워크플로우 시 한계 |

**결론**: scoring_config.yaml SOT가 유지보수 관점에서 가장 중요한 설계 결정.
