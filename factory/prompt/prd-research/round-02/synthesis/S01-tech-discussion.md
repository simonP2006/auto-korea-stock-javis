## 핵심 기술적 충돌 3가지

### 충돌 #1: MCP 통합 vs. 배치 파이프라인 자립성

- **T1/T4 발견**: pykrx-mcp는 대화형 ad-hoc 쿼리에 편리하나, 배치 파이프라인에서는 Python 직접 호출과 완전히 중복.
- **해결**: Phase 1은 MCP 없이 진행. Phase 2에서 대화형 탐색 UX 요구 시 DuckDB MCP 플러그인만 추가.
- **근거**: T4가 확인 — 파이프라인에서 MCP 비용은 "쿼리당 ~5줄 추가 Python" 대비 "MCP 서버 설정·유지보수" 부담이 불비례.

### 충돌 #2: VCP 탐지 복잡도 vs. Phase 1 실행 속도

- **T5 발견**: 전체 VCP(스윙 포인트 탐지 + 수축 측정)는 구현 복잡도 높고 오류 가능성 높음.
- **해결**: Phase 1은 **간소화된 프록시** 사용 — Bollinger Band 폭 수축 + 거래량 감소를 VCP 대리 지표로.
- **주의**: T5가 경고 — 프록시와 전체 VCP 사이의 경계가 모호. PRD에서 "Phase 1 프록시란 정확히 무엇인가" + "언제 전체 VCP로 전환하는가"를 명시해야.

### 충돌 #3: 시장 레짐 필터 포함 vs. 단순성

- **T5 발견**: VCP 성공률은 시장 조정기에 급락. KOSPI 200일 SMA 아래 = 전체 점수 신뢰도 하락.
- **해결**: 별도 경고 오버레이로 구현 ("현재 KOSPI 지수가 200일 이평선 하회 중 — 고점수 종목에도 주의"). 합산 점수에 포함하지 않음.
- **근거**: 점수에 레짐 필터를 포함하면 점수 해석이 비직관적이 됨(같은 90점이 시장 상황에 따라 다른 의미). 별도 경고가 더 투명.

- DuckDB 단일 파일 DB (분석 전용, T2/T4 확인)
